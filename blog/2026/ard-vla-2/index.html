ARD-VLA 2.0: closed-loop judging and role-aware action filtering

Created on October 25, 2026

2026   ·   ard-vla   closed-loop   task-planning   bimanual   co-vla   ·   research-notes

ARD-VLA 2.0 adds two things to the original ARD-VLA (1.0):

  1. Closed-loop judging and task planning, so the robot notices failures and recovers.
  2. Role-aware LAC, an inference-time filter that removes jitter without erasing deliberate two-arm coordination.

Part 1: Closing the loop

The problem: ARD-VLA 1.0 is open-loop

ARD-VLA 1.0 only produces actions. It never checks whether a step succeeded. If a grasp slips or an insertion misses, the model doesn’t notice. It moves on to the next step from a failed state and has no way to retry.

ARD-VLA 2.0 judges success at every step and plans around failures.

Architecture: one backbone, three branches

The judge is inspired by Laya, a “System 1” model that outputs only success/failure probabilities instead of generating text. Running a second VLM backbone just for judging would be expensive, so I kept SmolVLA’s SmolVLM2 backbone and borrowed only Laya’s output format.

A single backbone pass reads the camera image, the instruction, and the robot state once. Three branches share its features:

  • Judge and Selector heads decide what to do.
  • The action expert and ARD heads decide how to move.

The decision layer on top is a set of rules, not a trained module. Its decision sets the next cycle’s instruction and whether the action chunk gets executed.

One cycle

The runner observes and runs the backbone every cycle, but it uses the judgment only right after a subtask ends. While a subtask is in progress, the cost is one forward pass per chunk.

  • ADVANCE and RECOVER add one extra pass, because the instruction changes.
  • RETRY reuses the chunk produced at judging time.

So “one backbone pass” holds per chunk. Actual end-to-end latency still has to be measured with real weights.

Task planning in three layers

Layer When Who What it does
Task graph before execution a human (for fixed processes) or an LLM defines subtasks, their order, entry/exit conditions, allowed recoveries, and retry limits
In-execution selection after each subtask decision layer + Selector chooses the next node, a recovery, a recheck, or stop, but only among options the graph allows
Replanning after STOP a human or an LLM edits the graph itself from a safe pose (add steps, reorder, change recovery methods)

The order of steps (A → B → C) is fixed by the graph, and each step has several ways to reach the same goal. After each step the Judge decides success. On success the robot advances; on failure it picks another method for the same step and retries. If it still fails within the limit, the robot stops and the plan is revised.

How this differs from existing approaches

Compared with Their limitation ARD-VLA 2.0
Open-loop VLAs (SmolVLA, OpenVLA, ARD-VLA 1.0) never check success; move on from failed states judges every step and retries the same step with a different method
LLM planner + VLA replanning mid-execution takes seconds; can hallucinate steps or break format judging and selection fit inside one backbone pass; nothing is generated, so no invented steps
Separate VLM success detector a second model adds memory and latency shares the policy’s backbone and adds only small heads, so it targets a single consumer GPU
Symmetric bimanual VLAs can’t tell which arm caused a failure judges right-arm failures and left-arm slips separately, carrying role asymmetry into judging

Part 2: Role-aware LAC

Co-VLA’s LAC

Co-VLA (June 2026) proposes several ideas for coordinated bimanual control. The part I focused on is LAC (Latent-Aware Controller), a training-free filter applied at inference time. The easiest way to think about it is image stabilization for robot arms.

LAC splits each bimanual command into a shared motion that both arms make together and a residual motion that each arm makes on its own. It then asks whether the residual is meaningful or just jitter. Based on the answer, it decides at every step whether to follow the new command immediately or hold the previous motion and follow slowly.

The middle case is the key. When the two hands apply opposing forces, as in opening a bottle, LAC recognizes deliberate coordination and doesn’t filter it away.

Going one step further with arm roles

ARD-VLA assigns each arm a role from the start, so the filter can treat them differently:

  • The Stabilizer arm (holding the bottle) always suppresses jitter strongly and stays firm.
  • The Actuator arm (twisting the cap) responds quickly and follows the command as is during coordinated motion.

It’s like a person holding a nail steady with one hand while swinging a hammer with the other.

Implementation

ARD-VLA already builds each command as a base action plus a role-specific residual. I took those two terms out directly and used them as LAC’s shared and residual motion.

  • LAC sits at the point where commands are sent to the arms one step at a time (select_action()).
  • A single config option selects off / original LAC / role-aware LAC.
  • Gripper open/close commands pass through without filtering.

Status

These are design-level contributions. The closed-loop structure and LAC are implemented and pass tests with a tiny synthetic model, but they haven’t been trained or measured with real weights yet. LAC is not yet wired into the closed-loop path. Running everything in Isaac Sim is the next step once I have the hardware.
